# v3.0.0 API v2 and token research archive

This archive preserves the September 2, 2026 evaluation that created the
`v3.0.0` API v2 and token-contract slice. It is evidence and design input, not
an active release specification or proof of target behavior. Start with
`AGENTS.md`, `ESP32_CURRENT_STATUS.md`, the active development plan, and
`ESP32_V3_0_API_V2_TOKENS_PLAN.md`; load this file only when a v3.0 task needs
the detail below.

## Observed v1 web and API architecture

- The ADMIN console is one authenticated vanilla HTML/CSS/JavaScript document
  generated by `src/management-pages.c`; it uses no framework, CDN, remote
  fonts, external icon pack, WebSocket, or separate static-asset server.
- Management runs through ESP-IDF `esp_https_server` on `443`. It has a
  12 KiB HTTP-task stack, four open sockets, bounded request headers, a route
  capacity, and defensive no-store/CSP headers.
- FAT partitions mount as `/var` and `/usr` for NUT data. They do not serve the
  ADMIN UI. Upstream `data/html/` is not the ESP32 ADMIN UI.
- The browser performs one `GET /api/v1/status` on page load and every 15
  seconds when auto-refresh is enabled. It stores that preference in browser
  local storage. There is no WebSocket contract.

## v1 route and authorization inventory

| Route family | Current caller and authorization | v3.0 relevance |
| --- | --- | --- |
| `GET /api/v1/status` | ADMIN session, no activity refresh | Broad browser status payload; candidate for v2 resource redesign. |
| `GET /api/v1/agent/status` | diagnostic bearer | Shares the status serializer; a v1 field removal affects Agent consumers too. |
| `GET /api/v1/admin/logs` | ADMIN session, no activity refresh | Full volatile log ring; bearer tokens are rejected. |
| `POST /api/v1/admin/device`, `/time`, `/wifi`, `/password` | ADMIN session plus CSRF | Mutation response/error and form-contract review. |
| `/api/v1/admin/tokens` and `/diagnostic-tokens` | ADMIN session; CSRF for mutation | Token schema, scope, one-time display, and migration review. |
| `/api/v1/ota/check`, `/ota/install` | ADMIN session plus CSRF | Preserve local-update safety and bounded image handling. |
| `/api/v1/agent/ota/install` | OTA bearer | Must remain isolated from diagnostics and browser session behavior. |
| `/api/v1/agent/nut/disconnect` | diagnostic bearer | Test-only bounded diagnostic behavior; not a general control token. |

The exact registered v1 route inventory is in `src/management-routes.c`. The
browser callers are embedded in `src/management-pages.c`. The v3.0 planner
must re-audit both files rather than treating this table as complete evidence.

## Storage and runtime-memory findings

| Item | Observed source/configuration | Consequence |
| --- | --- | --- |
| Flash | 16 MiB configured/detected; only the lower 8 MiB is partitioned | Physical flash is not available as an app-slot budget without partition work. |
| OTA app slots | `app0` and `app1` are each `0x330000` = 3.1875 MiB | The assumption of two 8 MiB app slots is false. |
| PSRAM | Octal 80 MHz; runtime capacity from heap caps | Treat separately from internal heap. |
| ADMIN page | 49,152-byte bounded `calloc` per page generation | Large generated-page growth must be measured; allocator placement needs target evidence. |
| Status response | 7,000-byte bounded `calloc` per status request | Smaller serialized data alone does not lower allocation until this bound is justified and changed. |
| Runtime logs | 24-entry volatile ring, 191-character maximum message | Persistent RAM cost remains even if status stops serializing logs. |
| Full-log fetch | Heap snapshot of 24 entries plus bounded formatting buffers, only on explicit click | Keep chunked output and authorization isolation. |

The v1 hardware JSON reports three different values: `free_internal_bytes`,
`free_psram_bytes`, and `minimum_free_bytes`. The last is the historical
minimum free heap, not the total PSRAM capacity or a current free-memory value.
The displayed example of internal 150 KB and PSRAM 8.0 MB was a live-screen
snapshot, not a fixed device guarantee.

## Six-entry status-log evaluation

The current status serializer copies and JSON-serializes the newest six entries
from the 24-entry log ring. The same response serves both ADMIN and diagnostic
bearer status. Removing `logs` from v1 would therefore be a breaking schema
change and would narrow what diagnostic-bearer callers can read.

Observed benefits of removal:

- avoids the six-entry stack snapshot, timestamp formatting, escaping, JSON
  bytes, and log-lock work on each polling request;
- reduces browser parse/render work and may permit a smaller status buffer only
  after worst-case v2 size measurement;
- makes a dedicated Logs page the sole browser path for detailed log content.

Observed non-benefits:

- the 24-entry in-memory ring remains allocated;
- the fixed 7,000-byte status allocation remains until its bound changes;
- the ADMIN full-log endpoint still needs its bounded snapshot and chunked
  serialization when a user explicitly requests logs.

Decision: retain the v1 six-entry window. v3.0 is the authorized place to
design a lighter v2 status response and a dedicated Logs page, including
consumer migration, authorization, and resource evidence.

## UX redesign findings

The requested design direction is a dense commercial appliance interface:

- centered 1180–1280 px content shell, responsive side padding, no large
  desktop gutters;
- sticky desktop header with device identity, firmware, connection indicator,
  compact auto-refresh toggle/help, and accessible Sign Out;
- single-row desktop tabs and deliberate mobile overflow/menu behavior, never
  accidental two-row wrapping;
- browser-rendered lightweight gauges/indicators only for numeric data, with
  unavailable values rendered plainly and reduced-motion respected;
- formatted Device Status JSON using `JSON.stringify(data, null, 2)` for
  display while retaining exact v1 response text for Copy JSON;
- full-width bordered Hardware Diagnostics matching Runtime Logs;
- no framework or external assets by default.

Moving logs from Dashboard and Device Status to an explicit Logs page is a
presentation improvement. It meaningfully reduces normal-page complexity only
if the monolithic generated console is split into a smaller normal page and a
separate Logs document/route. Making Logs merely another hidden panel provides
little ESP32 memory benefit because the whole document is still generated.

## Constraints to carry into v3.0 design

- Preserve read-only UPS access, HTTPS `443`, NUT `3493`, and refused `8080`.
- Preserve ADMIN/CSRF boundaries and isolated OTA/diagnostic bearer scopes.
- Keep the device self-contained; do not add CDNs, remote fonts, external icon
  packs, or a JavaScript framework without a documented exceptional case.
- Build with ESP-IDF v6.0.2 for the ESP32-S3 target. Do not call source review
  a target resource measurement.
- No credentials, tokens, cookies, or Authorization values may enter this
  archive, test fixtures, logs, screenshots, or chat.
- Any v3.0 API break needs a named consumer, schema contract, error behavior,
  migration path, rollback behavior, and target acceptance evidence.
